# Eval Conventions — Canonical Metric Definitions

This document defines the authoritative meaning of every metric used in the benchmark. When writing analysis, queries, or dashboard code, always use these definitions. Deviations must be explicitly documented in the relevant spec.

---

## 1. Success / Resolve Rate

**Definition:** A task is **resolved** (`resolve_status = 'PASS'`) if and only if the SWE-bench hidden test suite passes 100% on the agent-generated patch, as determined by the official `sb-cli evaluate` command running inside Docker.

**Precise rules:**
- The evaluation is binary: PASS or FAIL. Partial credit does not exist.
- A patch that causes a test error (import error, syntax error, crash) counts as FAIL, not ERROR (ERROR is reserved for infrastructure failures — see below).
- If `sb-cli evaluate` itself crashes or times out, the task status is `ERROR` and it is **excluded** from the resolve rate denominator.
- Resolve rate = `resolved_tasks / (total_tasks - error_tasks)` × 100%.
- Report as both a fraction and a percentage: `3/5 (60.0%)`.

**Column in DB:** `task_results.resolve_status` ∈ `{PASS, FAIL, ERROR}`

---

## 2. Hallucination

**Definition:** An agent **hallucination** is any reference in a generated patch or plan to a file path, function name, class name, or module that does not exist in the repository at the commit SHA being evaluated.

**Detection method:** The Reviewer agent checks each `+` line in the patch against the repository's file tree and symbol index (built during Architect phase). A reference is flagged if:
- A file path appears in `diff --git a/<path>` but the file did not exist pre-patch AND was not created by an earlier hunk in the same patch.
- A function/class name is called or imported but does not appear in the repo's AST or in the patch's own added lines.

**Metric stored:** `task_results.hallucination_count` (integer, 0 = no hallucinations detected)

**Note:** Hallucination detection is heuristic. A count of 0 does not guarantee correctness; it only means the Reviewer found no phantom references.

---

## 3. Cost

**Definition:** Cost for a task (in USD) = Σ over all agent turns of:

```
(input_tokens × input_price_per_token) + (output_tokens × output_price_per_token)
```

Where prices come from `config/litellm_config.yaml` under each model's `input_cost_per_token` and `output_cost_per_token` fields (set at benchmark start time; not live-fetched).

**Column in DB:** `task_results.cost_usd` (NUMERIC(10,6))

**Run-level cost:** `benchmark_runs.total_cost_usd` = SUM of all task costs in the run.

**Important:** This is the cost of the **system agents** (open models via LiteLLM). It does **not** include any Claude Code (Anthropic subscription) usage by the developer.

---

## 4. Token Usage

**Definition:**
- `input_tokens`: total tokens sent to LLM APIs across all agent turns for a task (including system prompts, tool results, conversation history).
- `output_tokens`: total tokens generated by LLM APIs for a task.
- Both are summed across all agents (Architect + Developer + Tester + Reviewer) and all turns.

**Columns in DB:**
- `task_results.input_tokens` (INTEGER)
- `task_results.output_tokens` (INTEGER)

**Per-turn data:** `agent_events.input_tokens`, `agent_events.output_tokens`

---

## 5. Iteration Count

**Definition:** One **iteration** = one complete Developer↔Tester loop cycle. Specifically:

```
iteration N:
  1. Developer produces or revises a patch (1 Developer turn)
  2. Tester runs tests against the patch (1 Tester turn)
```

The Architect's initial planning turn and the Reviewer's final review turn are **not** counted as iterations.

**Counting rule:**
- `iteration_count = number of Developer turns` (since each Developer turn is paired with at most one Tester turn).
- Minimum = 1 (even if the first patch passes all tests).
- Maximum is bounded by `config/settings.yaml:max_iterations` (default: 5).

**Column in DB:** `task_results.iteration_count` (INTEGER)

**Why this matters:** High iteration counts (> 3) signal that the Developer is struggling. They correlate with higher cost and lower resolve rate on complex tasks.

---

## 6. Infrastructure Error vs. Task Failure

| Status | Meaning | Included in resolve rate? |
|--------|---------|--------------------------|
| `PASS` | Hidden tests pass | Yes (numerator + denominator) |
| `FAIL` | Hidden tests fail, but evaluation ran cleanly | Yes (denominator only) |
| `ERROR` | `sb-cli`, Docker, or DB infrastructure failed | **No** (excluded from both) |

**ERROR subcategories** (stored in `task_results.error_message`):
- `DOCKER_BUILD_FAIL` — sandbox image failed to build
- `PATCH_APPLY_FAIL` — `git apply` rejected the patch
- `TIMEOUT` — task exceeded `max_task_seconds`
- `DB_INSERT_FAIL` — metrics could not be saved
- `UNKNOWN` — catch-all

---

## 7. Baseline vs. Experimental Comparisons

When comparing single-agent (SOLVER=single) vs. multi-agent (SOLVER=multi):
- Always compare runs on the **same task set** (same `task_set` value).
- Resolve rate difference = `multi_rate - single_rate` (positive = multi wins).
- Cost ratio = `multi_total_cost / single_total_cost` (> 1.0 means multi costs more).
- Use the `benchmark_runs` table `solver_mode` column to filter.

## 8. Canonical SQL Snippets

**Overall resolve rate for a run:**
```sql
SELECT
  run_id,
  solver_mode,
  SUM(CASE WHEN resolve_status = 'PASS' THEN 1 ELSE 0 END)::float
    / NULLIF(SUM(CASE WHEN resolve_status != 'ERROR' THEN 1 ELSE 0 END), 0) AS resolve_rate,
  SUM(cost_usd) AS total_cost,
  AVG(iteration_count) AS avg_iterations
FROM task_results
WHERE run_id = '<run-id>'
GROUP BY run_id, solver_mode;
```

**Single vs. multi comparison on same task set:**
```sql
SELECT
  solver_mode,
  COUNT(*) FILTER (WHERE resolve_status = 'PASS') AS resolved,
  COUNT(*) FILTER (WHERE resolve_status != 'ERROR') AS evaluated,
  ROUND(SUM(cost_usd)::numeric, 4) AS total_cost_usd,
  ROUND(AVG(iteration_count)::numeric, 2) AS avg_iters
FROM task_results
JOIN benchmark_runs USING (run_id)
WHERE benchmark_runs.task_set = 'lite-5'
GROUP BY solver_mode;
```
