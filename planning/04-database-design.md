## 1. Design Goals and Constraints

Before the schema, the forces shaping it:

| Force | Consequence |
|---|---|
| Single-machine deployment, ≤ 50 tasks per run | No partitioning, no sharding. Simple is correct. |
| Results must be reproducible and auditable | Run records are **immutable after write**. No UPDATE on `run_records`. |
| The LLM cache must survive process restarts | Cache lives in Postgres, not in-process memory or Redis. |
| Dashboard reads must be fast for ad-hoc comparison | Three covering indexes on `run_records`; no joins needed for the summary table. |
| Multiple benchmark runs must be independently queryable | Every row in every table carries `run_id`. This is the primary isolation key. |
| Schema must be stable across the project lifetime | Additive-only migrations. No column renames or type changes after v1. |
| The scorer is LLM-free and writes nothing to the DB | `ScorerResult` is a transient Python object; it is consumed by `MetricsWriter` and then discarded. |

---

## 2. Entity Inventory

The database contains exactly **three tables**. This is intentional. Complexity is pushed into the application layer, not the schema.

| Table | Owner Module | Purpose | Mutability |
|---|---|---|---|
| `run_records` | `benchmark/metrics.py` via `TraceStore` | One row per (run, task) pair. The authoritative result record. | Immutable after insert |
| `trace_events` | `src/router/router.py` via `TraceStore` | One row per LLM call or tool event within a run. The audit log. | Immutable after insert |
| `llm_cache` | `src/router/cache.py` | One row per unique (model, messages) pair. Permanent response cache. | Insert-only; no deletes, no updates |

There is no `tasks` table, no `agents` table, no `sessions` table. Task definitions live in YAML files under `config/tasks/`. Agent identity is encoded as a string column in `trace_events`. Sessions are not a concept in this system.

## 3. Schema Definition

### 3.1 `run_records`

```sql
CREATE TABLE run_records (
    -- Identity
    run_id              UUID        NOT NULL,
    task_id             VARCHAR(255) NOT NULL,

    -- Configuration snapshot (what was running)
    solver_config       JSONB       NOT NULL,
    -- Stores the full SolverConfig as JSON, e.g.:
    -- {"solver": "multi", "max_dev_tester_iterations": 3,
    --  "max_dev_reviewer_iterations": 2, "max_tokens_per_task": 50000}

    -- Outcome
    outcome             VARCHAR(4)  NOT NULL CHECK (outcome IN ('PASS', 'FAIL')),
    test_output         TEXT        NOT NULL DEFAULT '',
    -- Truncated stdout+stderr from the scorer; stored for debugging.
    -- Not used in dashboard aggregations.

    -- Cost accounting
    total_cost_usd      NUMERIC(12, 8) NOT NULL DEFAULT 0,
    total_tokens        INTEGER     NOT NULL DEFAULT 0,

    -- Quality signals
    iteration_count     SMALLINT    NOT NULL DEFAULT 0,
    -- dev_tester_iterations + dev_reviewer_iterations
    hallucination_score NUMERIC(5, 4) NOT NULL DEFAULT 0,
    -- 0.0000 to 1.0000; four decimal places is sufficient precision

    -- Timing
    duration_seconds    NUMERIC(10, 3) NOT NULL DEFAULT 0,

    -- Bookkeeping
    created_at          TIMESTAMPTZ NOT NULL DEFAULT NOW(),

    -- Constraints
    PRIMARY KEY (run_id, task_id)
    -- Composite PK: a run_id can have many task_ids;
    -- a task_id can appear in many run_ids.
    -- The pair is unique and immutable.
);
```

**Notes on column choices:**

- `run_id UUID`: Generated by `benchmark/cli.py` at the start of each benchmark invocation. All tasks within one `make benchmark` call share the same `run_id`. This is the primary grouping key for the dashboard.
- `task_id VARCHAR(255)`: SWE-bench task IDs are strings like `django__django-11099`. Custom task IDs are user-defined. 255 chars is a safe upper bound.
- `solver_config JSONB`: Storing the full config as JSONB rather than normalizing it into columns means the schema does not need to change when new solver parameters are added. The dashboard filters on `solver_config->>'solver'` using a generated column index (see §7).
- `outcome VARCHAR(4)`: A CHECK constraint is more reliable than an enum type for this use case because adding a new outcome value (e.g., `'SKIP'`) requires only a constraint change, not a type migration.
- `test_output TEXT`: Unbounded text. In practice, scorer output is truncated to 32 KB by the scorer before writing. No database-level truncation is applied; the application is responsible.
- `total_cost_usd NUMERIC(12, 8)`: Eight decimal places because per-token costs for open models are on the order of $0.000001. `NUMERIC` avoids floating-point rounding errors in aggregations.
- `hallucination_score NUMERIC(5, 4)`: Range 0.0000–1.0000. Four decimal places.
- `created_at TIMESTAMPTZ`: Always UTC. The application never writes naive datetimes.

### 3.2 `trace_events`

```sql
CREATE TABLE trace_events (
    -- Identity
    event_id            UUID        NOT NULL PRIMARY KEY,
    run_id              UUID        NOT NULL,
    task_id             VARCHAR(255) NOT NULL,

    -- Attribution
    agent_role          VARCHAR(32) NOT NULL,
    -- One of: 'architect', 'developer', 'tester', 'reviewer', 'system'
    -- 'system' is used for budget_exceeded and harness-level events.
    turn_index          SMALLINT    NOT NULL,
    -- Monotonically increasing within a (run_id, task_id, agent_role).
    -- Starts at 0. Used to reconstruct the conversation timeline.

    -- Event classification
    event_type          VARCHAR(32) NOT NULL,
    -- One of: 'llm_call', 'tool_call', 'tool_error', 'budget_exceeded', 'cache_hit'

    -- LLM call fields (NULL for tool_call and tool_error events)
    model               VARCHAR(128),
    prompt_tokens       INTEGER,
    completion_tokens   INTEGER,
    cost_usd            NUMERIC(12, 8),
    cache_hit           BOOLEAN     NOT NULL DEFAULT FALSE,

    -- Arbitrary event payload
    payload             JSONB       NOT NULL DEFAULT '{}',
    -- For llm_call: {"messages_hash": "...", "temperature": 0.2}
    -- For tool_call: {"server": "filesystem", "tool": "read_file",
    --                 "arguments": {"path": "src/foo.py"}, "result_ok": true}
    -- For tool_error: {"server": "runcode", "tool": "exec",
    --                  "error": "ToolDeniedError: curl is not allowed"}
    -- For budget_exceeded: {"tokens_used": 50001, "cap": 50000}

    -- Bookkeeping
    created_at          TIMESTAMPTZ NOT NULL DEFAULT NOW(),

    -- Foreign key to run_records
    -- Declared but NOT enforced with a FK constraint (see §11.2)
    -- run_id + task_id reference run_records(run_id, task_id)
);
```

**Notes on column choices:**

- `event_id UUID PRIMARY KEY`: Each event is independently addressable. The router generates this UUID before writing.
- `agent_role VARCHAR(32)`: A short string rather than a foreign key to an agents table. Agent identity is stable and enumerable; a lookup table adds no value.
- `turn_index SMALLINT`: Allows reconstruction of the exact sequence of events within a node's execution. The developer node's tool-use loop produces multiple events per invocation; `turn_index` distinguishes them.
- `event_type VARCHAR(32)`: Extensible without a migration. New event types can be added by the application without touching the schema.
- LLM-specific columns (`model`, `prompt_tokens`, `completion_tokens`, `cost_usd`, `cache_hit`): These are NULL for non-LLM events. The alternative — separate tables for each event type — would complicate the dashboard query and add no benefit at this scale.
- `cache_hit BOOLEAN NOT NULL DEFAULT FALSE`: Explicit column rather than encoding in `payload` because the dashboard aggregates on it (`WHERE cache_hit = FALSE` to compute real spend).
- `payload JSONB`: The escape valve. Every event type can carry arbitrary structured data without a schema migration. The dashboard does not query inside `payload`; it is for debugging and trace replay only.

### 3.3 `llm_cache`

```sql
CREATE TABLE llm_cache (
    -- Identity
    cache_key           VARCHAR(64) NOT NULL PRIMARY KEY,
    -- SHA-256 hex digest of (model_name || canonical_json(messages)).
    -- 64 hex chars = 256 bits. Collision probability is negligible.

    -- Cached response
    model               VARCHAR(128) NOT NULL,
    content             TEXT        NOT NULL,
    -- The full text content of the LLM response.

    tool_calls          JSONB,
    -- NULL if the response contained no tool calls.
    -- Stored as a JSON array of ToolCall objects if present.

    prompt_tokens       INTEGER     NOT NULL,
    completion_tokens   INTEGER     NOT NULL,
    cost_usd            NUMERIC(12, 8) NOT NULL,
    -- Cost at time of original call. Replayed responses report cost_usd = 0
    -- in TraceEvents (cache_hit=True), but the original cost is preserved here
    -- for reference.

    -- Bookkeeping
    created_at          TIMESTAMPTZ NOT NULL DEFAULT NOW()
    -- No updated_at. Cache entries are never modified.
);
```

**Notes on column choices:**

- `cache_key VARCHAR(64) PRIMARY KEY`: The SHA-256 hex digest is the natural primary key. No surrogate key is needed.
- No `run_id` column: The cache is intentionally **cross-run**. A response cached in run A is reused in run B if the model and messages are identical. This is the reproducibility mechanism. Associating cache entries with a specific run would defeat the purpose.
- No TTL column: Cache entries are permanent. This is a deliberate design choice documented in §9.
- `tool_calls JSONB`: NULL when absent rather than an empty array, to distinguish "this model does not support tool calls" from "this call had no tool calls."
- `cost_usd` stored at original call time: When a cache hit occurs, the `TraceEvent` records `cost_usd = 0` and `cache_hit = TRUE`. The `llm_cache` row preserves the original cost for auditing purposes (e.g., "how much would this run have cost without caching?").

## 4. Entity Relationships

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                                                                             │
│   run_records                    trace_events                              │
│   ──────────────────────         ──────────────────────────────────────    │
│   run_id  (UUID)    ◄────────── run_id  (UUID)                            │
│   task_id (VARCHAR) ◄────────── task_id (VARCHAR)                         │
│                                                                             │
│   [composite PK: run_id + task_id]    [PK: event_id]                      │
│                                                                             │
│   One run_record has many trace_events.                                    │
│   The relationship is (run_id, task_id) → many events.                    │
│                                                                             │
│                                                                             │
│   llm_cache                                                                │
│   ──────────────────────                                                   │
│   cache_key (VARCHAR)  [PK]                                                │
│                                                                             │
│   No foreign keys. The cache is a standalone lookup table.                 │
│   trace_events.payload may contain a cache_key reference for debugging,   │
│   but there is no enforced FK relationship.                                │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

### 4.1 Cardinalities

| Relationship | Cardinality | Notes |
|---|---|---|
| `run_records` → `trace_events` | One-to-many | One (run_id, task_id) pair produces 5–50 trace events in a typical multi-agent run |
| `run_records` → `llm_cache` | None (logical only) | Cache entries are referenced by hash, not by FK |
| `trace_events` → `llm_cache` | None (logical only) | A cache-hit event's `payload` may include the `cache_key` for debugging |

### 4.2 Why No Enforced Foreign Key from `trace_events` to `run_records`

The router writes `TraceEvent` rows **synchronously during the LLM call**, before the graph completes and before `MetricsWriter` writes the `RunRecord`. If a hard FK constraint existed, every trace event write would fail because the parent `run_record` does not yet exist.

The options were:

1. **Write the `RunRecord` first with a placeholder outcome, then update it.** Rejected: violates the immutability requirement.
2. **Buffer all trace events in memory and write them after the RunRecord.** Rejected: if the process crashes mid-run, all trace data is lost.
3. **Declare the FK in the schema but do not enforce it (`NOT VALID`).** Rejected: misleading; tools that read the schema would assume referential integrity.
4. **No FK constraint; document the logical relationship.** Chosen. The application guarantees that every `trace_events` row has a corresponding `run_records` row by the end of a successful run. Orphaned trace events (from crashed runs) are acceptable and queryable.

The `TraceStore.get_trace_events(run_id)` method returns events regardless of whether a corresponding `run_record` exists, which is the correct behavior for debugging crashed runs.

## 5. Data Ownership by Module

Ownership means: **only this module may write to these columns**. All other modules are read-only consumers.

### 5.1 `run_records` Ownership

| Column | Owner | Written When |
|---|---|---|
| `run_id` | `benchmark/cli.py` | Generated at benchmark start; passed through to all components |
| `task_id` | `benchmark/loader.py` | Loaded from task YAML; immutable for the lifetime of the run |
| `solver_config` | `benchmark/driver.py` | Serialized from `SolverConfig` at driver instantiation |
| `outcome` | `benchmark/scorer.py` → `benchmark/metrics.py` | `ScorerResult.outcome` passed to `MetricsWriter.write()` |
| `test_output` | `benchmark/scorer.py` → `benchmark/metrics.py` | `ScorerResult.test_output` passed to `MetricsWriter.write()` |
| `total_cost_usd` | `benchmark/metrics.py` | Summed from `trace_events.cost_usd` for this (run_id, task_id) |
| `total_tokens` | `benchmark/metrics.py` | Summed from `trace_events.prompt_tokens + completion_tokens` |
| `iteration_count` | `benchmark/metrics.py` | Read from `GraphState.dev_tester_iterations + dev_reviewer_iterations` |
| `hallucination_score` | `src/metrics/hallucination.py` → `benchmark/metrics.py` | Computed by `HallucinationChecker.check()` |
| `duration_seconds` | `benchmark/driver.py` → `benchmark/metrics.py` | Wall-clock time of `graph.invoke()` |
| `created_at` | Postgres `DEFAULT NOW()` | At insert time; never set by application code |

**Invariant:** `benchmark/metrics.py` is the sole writer of `run_records` rows. No other module calls `TraceStore.write_run_record()`.

### 5.2 `trace_events` Ownership

| Column | Owner | Written When |
|---|---|---|
| `event_id` | `src/router/router.py` | Generated by `uuid.uuid4()` before each write |
| `run_id`, `task_id` | Passed from `GraphState` | Set at graph invocation; never modified |
| `agent_role` | Each agent node | Hardcoded string per node: `'architect'`, `'developer'`, etc. |
| `turn_index` | Each agent node | Incremented per turn within the node |
| `event_type` | `src/router/router.py` | `'llm_call'` for LLM events; MCP servers write `'tool_call'` / `'tool_error'` events via the same `TraceStore` |
| `model` | `src/router/router.py` | Resolved from `RouterConfig.tier_to_model[tier]` |
| `prompt_tokens`, `completion_tokens` | `src/router/router.py` | Extracted from LiteLLM response `usage` object |
| `cost_usd` | `src/router/router.py` | Computed as `tokens × price` from `RouterConfig` |
| `cache_hit` | `src/router/router.py` | `True` if `ResponseCache.get()` returned a hit |
| `payload` | Event-type-specific | Router sets LLM payload; MCP servers set tool payload |
| `created_at` | Postgres `DEFAULT NOW()` | At insert time |

**Invariant:** `trace_events` rows are written in two places:
1. `src/router/router.py` — for every LLM call (hit or miss).
2. MCP server dispatcher — for every tool call and tool error.

Both paths use `TraceStore.write_trace_event()`. No other code path writes to `trace_events`.

### 5.3 `llm_cache` Ownership

| Column | Owner | Written When |
|---|---|---|
| `cache_key` | `src/router/cache.py` | Computed as `sha256(model + canonical_json(messages))` |
| `model` | `src/router/cache.py` | Copied from `LLMRequest.model` |
| `content` | `src/router/cache.py` | Copied from `LLMResponse.content` |
| `tool_calls` | `src/router/cache.py` | Copied from `LLMResponse.tool_calls`; NULL if absent |
| `prompt_tokens`, `completion_tokens`, `cost_usd` | `src/router/cache.py` | Copied from the original `LLMResponse` |
| `created_at` | Postgres `DEFAULT NOW()` | At insert time |

**Invariant:** `src/router/cache.py` is the sole writer and reader of `llm_cache`. No other module accesses this table.

### 5.4 Read Access by Module

| Module | Tables Read | Purpose |
|---|---|---|
| `dashboard/app.py` | `run_records`, `trace_events` | Render comparison table and cost/iteration plots |
| `benchmark/metrics.py` | `trace_events` (indirectly, via summing in-memory state) | Compute `total_cost_usd` and `total_tokens` for the run record |
| `src/router/cache.py` | `llm_cache` | Cache lookup before every LLM call |
| `src/metrics/trace_store.py` | `run_records`, `trace_events` | `get_run_records()` and `get_trace_events()` for dashboard and debugging |

The scorer (`benchmark/scorer.py`) reads **nothing** from the database. It is a pure function of `Task` and `patch`.

## 6. Multi-Tenancy Model

### 6.1 Definition of "Tenant"

This system has no user accounts, no authentication, and no concurrent users. The concept of multi-tenancy in the traditional sense (isolating data between organizations or users) does not apply.

However, the system does need to isolate **benchmark runs** from each other, because:
- Multiple runs may be compared in the dashboard.
- A run with `solver=multi` must not contaminate the metrics of a run with `solver=single`.
- A crashed or partial run must not corrupt the records of a completed run.

The `run_id` (UUID4) is the **run-level isolation key**. It plays the role that a tenant ID plays in a multi-tenant SaaS system.

### 6.2 Run Isolation Guarantees

| Concern | Mechanism |
|---|---|
| Result isolation | Every `run_records` row has a `run_id`. Dashboard queries always filter by `run_id` or group by it. |
| Trace isolation | Every `trace_events` row has a `run_id`. `TraceStore.get_trace_events(run_id)` returns only events for that run. |
| Cache sharing | `llm_cache` is intentionally **shared across runs**. This is correct: if two runs ask the same model the same question, the second run should get the cached answer. Cache entries have no `run_id`. |
| Budget isolation | `BudgetGuard` tracks tokens per `run_id` in memory. Each run starts with a fresh budget. |
| Sandbox isolation | Each task execution gets its own Docker container with its own volume mount at `/sandbox/repo/{task_id}`. Containers are `--rm`; no state persists between tasks or runs. |

### 6.3 Partial Run Recovery

If a benchmark run crashes mid-way (e.g., process killed, OOM):

- `run_records` rows for completed tasks are already written and immutable. They are correct.
- `trace_events` rows for all completed and in-progress tasks are written. Orphaned events (for the task that was in-flight when the crash occurred) have no corresponding `run_record`. This is acceptable; they are queryable for debugging.
- The `llm_cache` is unaffected; it is written per-call, not per-run.
- Re-running with the same `run_id` is not supported. The CLI always generates a fresh `run_id`. Partial runs are not resumed; they are re-run from scratch with a new `run_id`.

### 6.4 Parallel Run Safety

The architecture document notes that `--parallel N` is architecturally supported but not implemented. The schema is safe for parallel runs because:

- `run_records` PRIMARY KEY is `(run_id, task_id)`. Two parallel tasks with different `task_id`s under the same `run_id` cannot collide.
- `trace_events` PRIMARY KEY is `event_id` (UUID4). UUID4 collisions are negligible.
- `llm_cache` uses `INSERT ... ON CONFLICT DO NOTHING`. Concurrent inserts of the same cache key are safe; the first writer wins.
- `BudgetGuard` uses a `threading.Lock` around its in-memory dict, as documented in the system design.

No schema changes are required to enable parallel execution.

## 7. Indexes and Query Patterns

### 7.1 Index Definitions

```sql
-- run_records: primary access patterns for the dashboard

-- 1. Fetch all records for a specific run (most common dashboard query)
CREATE INDEX idx_run_records_run_id
    ON run_records (run_id);

-- 2. Fetch all records for a specific task across all runs (comparison view)
CREATE INDEX idx_run_records_task_id
    ON run_records (task_id);

-- 3. Filter by solver type (dashboard: "show only multi-agent runs")
--    Uses a generated column to avoid full JSONB scan.
ALTER TABLE run_records
    ADD COLUMN solver_type VARCHAR(16)
    GENERATED ALWAYS AS (solver_config->>'solver') STORED;

CREATE INDEX idx_run_records_solver_type
    ON run_records (solver_type);

-- 4. Filter by outcome (dashboard: "show only PASS results")
CREATE INDEX idx_run_records_outcome
    ON run_records (outcome);

-- trace_events: primary access patterns for debugging and dashboard drill-down

-- 5. Fetch all events for a run (trace replay, debugging)
CREATE INDEX idx_trace_events_run_id
    ON trace_events (run_id);

-- 6. Fetch all events for a specific (run, task) pair (task-level drill-down)
CREATE INDEX idx_trace_events_run_task
    ON trace_events (run_id, task_id);

-- 7. Fetch all LLM call events (cost aggregation queries)
CREATE INDEX idx_trace_events_event_type
    ON trace_events (event_type)
    WHERE event_type = 'llm_call';

-- llm_cache: only accessed by primary key lookup; no additional indexes needed.
-- The cache_key VARCHAR(64) PRIMARY KEY is already a B-tree index.
```

### 7.2 Expected Query Patterns

**Dashboard: summary comparison table**
```sql
-- All runs, grouped by solver type, with aggregate metrics
SELECT
    run_id,
    solver_config->>'solver'    AS solver,
    COUNT(*)                    AS task_count,
    SUM(CASE WHEN outcome = 'PASS' THEN 1 ELSE 0 END) AS pass_count,
    AVG(total_cost_usd)         AS avg_cost_usd,
    AVG(iteration_count)        AS avg_iterations,
    AVG(hallucination_score)    AS avg_hallucination,
    MIN(created_at)             AS run_started_at
FROM run_records
GROUP BY run_id, solver_config->>'solver'
ORDER BY run_started_at DESC;
-- Uses: idx_run_records_run_id (grouping), idx_run_records_solver_type (filter)
```

**Dashboard: per-task drill-down**
```sql
-- All results for a specific task across all runs
SELECT
    r.run_id,
    r.solver_config->>'solver'  AS solver,
    r.outcome,
    r.total_cost_usd,
    r.iteration_count,
    r.hallucination_score,
    r.duration_seconds
FROM run_records r
WHERE r.task_id = $1
ORDER BY r.created_at DESC;
-- Uses: idx_run_records_task_id
```

**Dashboard: cost breakdown by agent role**
```sql
-- Total cost per agent role for a specific run
SELECT
    agent_role,
    SUM(cost_usd)               AS total_cost,
    COUNT(*)                    AS call_count,
    SUM(CASE WHEN cache_hit THEN 1 ELSE 0 END) AS cache_hits
FROM trace_events
WHERE run_id = $1
  AND event_type = 'llm_call'
GROUP BY agent_role
ORDER BY total_cost DESC;
-- Uses: idx_trace_events_run_id, idx_trace_events_event_type
```

**Debugging: full trace for a crashed task**
```sql
-- All events for a specific (run, task) pair in chronological order
SELECT
    event_id,
    agent_role,
    turn_index,
    event_type,
    model,
    prompt_tokens,
    completion_tokens,
    cost_usd,
    cache_hit,
    payload,
    created_at
FROM trace_events
WHERE run_id = $1 AND task_id = $2
ORDER BY created_at ASC, turn_index ASC;
-- Uses: idx_trace_events_run_task
```

### 7.3 What Is Not Indexed

- `trace_events.agent_role`: Low cardinality (5 values), but not a primary filter in any dashboard query. Added to `GROUP BY` after filtering by `run_id`.
- `trace_events.created_at`: Ordering only; not a filter predicate. The composite index on `(run_id, task_id)` is sufficient.
- `run_records.created_at`: Used for `ORDER BY` in the dashboard summary query. At ≤ 50 rows per run and ≤ 100 runs total (5,000 rows maximum), a sequential scan on `created_at` is faster than an index scan.
- `llm_cache.created_at`: Never queried. Present for auditing only.

## 8. Immutability and Audit Properties

### 8.1 Immutability Rules

| Table | Rule | Enforcement |
|---|---|---|
| `run_records` | No UPDATE, no DELETE after insert | `INSERT ... ON CONFLICT (run_id, task_id) DO NOTHING` in `TraceStore.write_run_record()`. The Postgres role used at runtime has no UPDATE privilege on this table. |
| `trace_events` | No UPDATE, no DELETE after insert | The Postgres runtime role has INSERT and SELECT only on `trace_events`. No UPDATE privilege. |
| `llm_cache` | No UPDATE, no DELETE after insert | `INSERT ... ON CONFLICT (cache_key) DO NOTHING`. The runtime role has INSERT and SELECT only. |

### 8.2 Postgres Role Separation

Two Postgres roles are used:

```sql
-- Migration role (used only by `alembic upgrade head` during `make setup`)
CREATE ROLE swe_admin WITH LOGIN PASSWORD '...' CREATEDB;
GRANT ALL PRIVILEGES ON DATABASE swe_benchmark TO swe_admin;

-- Runtime role (used by the application at all times)
CREATE ROLE swe_app WITH LOGIN PASSWORD '...';
GRANT CONNECT ON DATABASE swe_benchmark TO swe_app;
GRANT USAGE ON SCHEMA public TO swe_app;

-- run_records: INSERT and SELECT only
GRANT INSERT, SELECT ON run_records TO swe_app;

-- trace_events: INSERT and SELECT only
GRANT INSERT, SELECT ON trace_events TO swe_app;

-- llm_cache: INSERT and SELECT only
GRANT INSERT, SELECT ON llm_cache TO swe_app;

-- Sequences (for any auto-generated IDs, though all PKs are UUIDs)
GRANT USAGE ON ALL SEQUENCES IN SCHEMA public TO swe_app;
```

The `DATABASE_URL` in `.env` uses the `swe_app` credentials. The `swe_admin` credentials are used only in `make setup` and are never present in the application environment.

### 8.3 Audit Trail Completeness

A complete audit trail for any benchmark run can be reconstructed from the database alone:

1. **What ran:** `run_records.solver_config` (full JSON snapshot of `SolverConfig`).
2. **What happened:** `trace_events` ordered by `(run_id, task_id, created_at, turn_index)`.
